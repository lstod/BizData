----------------------------------------------------------------------
1. the question this run existed to answer
----------------------------------------------------------------------

  Can Cowork's sandbox make an outbound HTTPS PUT to a presigned URL?

  YES.

  Both artifacts are in the bucket, written by the agent through presigned
  URLs the server minted. Nothing else in the build could have established
  this, and the whole publish path rested on it.

    $ aws s3 ls s3://bizdata-runs-142940389238/runs/delivery-review-2026-08-r1/

  Four objects. The two artifacts land six and seven seconds before the two
  the server writes, which is the two-phase shape visible in the timestamps:
  the agent's uploads complete, then the finalising call heads each key and
  only then writes the log and the ledger.

----------------------------------------------------------------------
5. the Drive save did not happen, and the reason is a finding
----------------------------------------------------------------------

  The one Done-when condition this run did not meet.

  The run created the Drive folder, so it can write to Drive. What it could
  not do is put a file there:

    "the Drive connector only accepts file content inline in the request, and
     re-encoding a 48 KB deck through that path risks silent corruption -- not
     something I'll do to a partner deliverable"

  A text-only file surface cannot carry a .pptx or a .xlsx. The run declined
  rather than base64ing a binary through a field meant for text and hoping,
  which is the right call: a corrupt deck that opens is worse than no deck.

  So the run-id-in-filename convention -- engagement-book-2026-08-<run_id>.xlsx
  -- is specified in two Skills and remains unexercised. It is not wrong; it
  is untested, and the reason is upstream of it.
