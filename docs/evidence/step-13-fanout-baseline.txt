Note assertion 7, which is the one that proves overlap rather than suggesting it. latency_ms
is measured inside each handler, so a run whose wall clock is below the sum of its own
handler times must have had handlers running at the same time. 1.54s of wall against 3.06s
of handlers is not a fast run, it is two runs at once. Assertion 6 is the control: the
sequential run's wall clock sits above its own sum, as it must.

Note also assertion 4. Handler time goes UP under fan-out, by 32% here. That is contention,
it is real, and it is the cost being traded for the wall clock. The check is a floor rather
than a tolerance: contention can only add time, so a parallel run whose handlers took
materially LESS time did less work, and that is the failure worth catching. What "the same
work" actually rests on is assertion 3, which compares the call multiset out of the
tool-call log -- every tool, every argument, counted -- and is exact.

1.07x. Handler time nearly quadrupled -- 4.64s to 19.23s -- while the wall clock did not
move. Each call absorbed almost exactly the queueing delay of the calls beside it, which is
the signature of work arriving at something that can only do one thing at a time.

The interesting question is what. Two causes look identical from outside and have opposite
implications: a path that cannot run two calls at once, which would be a defect in this
design, or a database with no spare CPU, which is a line item. The pg_sleep control
separates them, because pg_sleep holds a connection without consuming any CPU:

    8 concurrent sleeps of 0.5s finished in 0.58s, against 4.67s sequential. 8.0x.

So the path overlaps perfectly. The shared boto3 client, the RDS Data API, anyio's worker
threads and the MCP dispatcher are all fine -- the SDK spawns tools/call into its task group
(only `initialize` is inline) and runs synchronous handlers through anyio.to_thread. Nothing
in the chain serialises.

What is left is the cluster:

    "MinCapacity": 0.0,
    "MaxCapacity": 1.0,
    "SecondsUntilAutoPause": 86400

One ACU. The queries are CPU-bound and there is roughly a quarter of a vCPU to run them on,
so eight of them at once is eight of them in a queue. The fan-out was working the whole
time; there was nothing to fan out onto.

fan-out's benefit is bounded by cluster capacity rather than by the design, that the two are
separable, and that moving between them is one variable and no code.


================================================================================
4. THE CEILING, AND WHY IT IS NOT CONCURRENCY
================================================================================

Concurrency swept on both backends, median of one run each:

    local Postgres                      Aurora at 8 ACU
    c=2    2.50s -> 1.87s   1.34x       c=2    4.26s -> 3.08s   1.38x
    c=4    2.48s -> 1.60s   1.55x       c=4    4.11s -> 2.92s   1.41x
    c=8    2.51s -> 1.54s   1.63x       c=8    4.13s -> 3.28s   1.26x
    c=16   2.46s -> 1.48s   1.67x       c=16   4.14s -> 2.91s   1.42x

It plateaus by four, and doubling again buys nothing. That is not a capacity limit and not a
tuning failure -- it is Amdahl's law meeting the line drawn in this step.

Only twenty of the twenty-six calls are in the fan-out. The other six are the run ledger,
four pages of list_engagements and the portfolio-wide get_time_summary, and every one of
them is sequential *by design*: the ledger decides whether the run should happen at all, the
portfolio has to be complete before anything is chosen, and the coverage call is deliberately
unscoped because a subset-scoped version measures a different quantity. Those six are also
the expensive ones -- list_engagements computes the whole health view. Perfect fan-out of the
remaining twenty leaves the six untouched, and the six are most of the run.

So the measured ceiling is a direct consequence of where the line was drawn, and it is worth
saying plainly: the sequential part is sequential because it must be, not because it was not
got to. Widening the fan-out to cover triage would beat this number and produce a pack that
cannot be trusted -- which is the thing this repo has now learned three times, and the reason
SKILL.md step 4a says out loud that it is not the fan-out step 4 warns about.


================================================================================
5. THAT IT IS THE SAME PACK
================================================================================

Asserted three ways, on every run above.

The call multiset (assertion 3), out of the tool-call log rather than out of the harness's
intentions: same tools, same arguments, same counts, order deliberately discarded because
order is the one thing fan-out is supposed to change.

The pack (assertion 9), compared after stripping run_id recursively. Recursively matters:
every tool response carries its own run_id from the base Response model in
server/tools/common.py, so a top-level strip leaves a dozen nested differences that mean
nothing. The two dicts key in `chosen` order at any concurrency because asyncio.gather
returns in the order it was given, so completion order never leaks into the file.

The workbook (assertions 11 and 12), cell by cell. Not a checksum: build_workbook.py opens a
bare Workbook() and openpyxl stamps dcterms:created and current zip mtimes, so two
byte-different files are the normal result of one unchanged pack. check_pack.compare_workbooks
loads without data_only -- so the three live columns compare as formula text rather than as
the None Excel never filled in -- and walks every cell's value and number format across all
five tabs.

It finds exactly one difference, every time, and it is the right one:

    Summary!B3: 'fanout-seq-3' vs 'fanout-par-3'

The run id, which is two runs' worth of two different run ids and is supposed to differ --
step 12 requires a regenerated pack to take a new one, so two workbooks carrying the same id
would be the defect. Asserted in both directions: that it is the only difference before it is
accounted for, and that renaming it leaves nothing at all between the two files.
