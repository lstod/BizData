2. why it authenticated, and what that does not prove
-----------------------------------------------------------------------

What is established server-side, and none of it depends on reading Cowork's UI:

  a. **No dynamic client registration happened.** The user pool holds exactly two app
     clients, `cowork-connector` and `bizdata-test-machine`, both created 2026-08-20.
     Nothing was created during the install. Had Cowork fallen back to DCR it would
     have failed, since Cognito does not support it.

  b. **The token can only have come from `cowork-connector`.** server/auth.py rejects
     any token whose `client_id` is not in BIZDATA_OAUTH_CLIENT_ID, which holds those
     two ids. The other is client_credentials-only and is used by check_auth.py. A
     browser-flow token from `Claude-User` is the connector client.

  c. **That client is confidential.** It carries a 52-character secret, and its token
     endpoint refuses an exchange without one — measured, `invalid_client` /
     `invalid_client_secret`, against `invalid_grant` when the secret is supplied.
     See step-10-local-plugin-proof.txt §4.

  d. **Nothing re-authenticated during the run.** Every request in the window logged
     `"authenticated": true`, 67 × 200 and 0 × 401. There was no failed attempt, no
     retry, no fresh authorization.

  e. **A prior authorization was still live.** The app client's refresh token validity
     is 30 days and its access token 60 minutes. The connector was hand-registered
     with its client id *and secret* at steps 4–5 on 2026-08-20 and used for the Cowork
     runs at steps 8 and 9 on 2026-08-23 — one day before this run.

So the conclusion the evidence supports is:

    The plugin's declared connector resolved to an authorization this workspace
    already held. No credential was needed because one had already been supplied,
    by hand, four days earlier.

And the conclusion it does **not** support:

    That a plugin-installed connector authenticates a confidential client with no
    secret. Nothing here shows that, and (c) says it cannot.

This distinction is the whole finding and it is worth not rounding off. A demo on this
machine looks like a one-step install. A fresh workspace — a reviewer, a new laptop, a
different account — would hit the token endpoint with no stored credential, and (c)
says what happens then.


-----------------------------------------------------------------------
2a. the disconnect/reconnect test — run 2026-08-24, finding closed
-----------------------------------------------------------------------

Disconnected the connector on the plugin's connector page, then reconnected from the
plugin alone, adding no custom connector.

  Result:  it reconnected with **nothing entered** — no client id, no secret.
           It also **retained the "always allow" tool permissions** set before the
           disconnect.

Taken alone the first line looks like the larger finding: a plugin connector completing
OAuth against a confidential client with no credential. It is not, and the second line
is what shows why.

**The retained permissions are the tell.** Per-tool permissions are connector-scoped
user state. Had Disconnect actually forgotten the connector they would have reset to
defaults. They did not, so Disconnect preserves connector-scoped state — and a stored
OAuth credential is connector-scoped state of exactly the same kind.

**The protocol closes it independently of any UI reading.** The remaining question was
whether Cowork completed a fresh authorization or merely refreshed an existing one. It
does not matter, because *both* require the secret. Measured against Cognito, same
discriminator as §4 of the local proof:

    refresh, no secret         400  {"error":"invalid_client",
                                     "error_description":"invalid_client_secret"}
    refresh, secret via Basic  400  {"error":"invalid_grant"}

Refresh is not a way around client authentication. Access tokens here last 60 minutes,
so a connector still working an hour later is one that can mint new tokens, and minting
requires the secret whichever grant is used.

    Therefore Cowork holds the client secret and retained it through Disconnect.

Two independent lines of evidence agreeing — one observable in the UI, one measured at
the token endpoint. §2's conservative reading is confirmed rather than overturned, and
it is worth noting that the test's headline result pointed the other way. The
corroborating detail is what made it decidable.

**The one case still untested by hand now has a known answer.** A workspace that never
supplied the secret cannot authenticate this connector. That is no longer an inference:
every grant type the client supports requires client authentication, and a manifest
cannot carry the credential, so a fresh workspace has nothing to present.

**A smaller finding, and it belongs in SECURITY.md.** "Disconnect" does not revoke. It
ends the session and keeps both the credential and the tool permissions. A user who
disconnects a connector intending to withdraw its access has not done that, and nothing
in the UI says so. Worth a line at step 11 — the gap between what a control is called
and what it does is exactly what a security reviewer asks about.

5. a real defect the run surfaced, and the self-check caught it
-----------------------------------------------------------------------

The run's own narrative: *"Slide 1 shows 'Scoring model n/a' — checking where the
builder reads it from."* It then added the value and rebuilt both files in order.

This is not a packaging regression. `plugin/skills/` was untouched by step 10 — git
confirms it — and the defect is a three-way disagreement that predates the plugin:

  assemble-delivery-pack/SKILL.md   the documented pack.json shape has **no**
                                    top-level scoring_model_version at all
  build_workbook.py:373             reads it top-level, and **falls back** to
                                    pack["time_summary"]["scoring_model_version"]
  build_deck.py:301,594             reads it top-level only, no fallback ->
                                    renders the literal string "n/a"

The tools return `scoring_model_version` inside every response, so the natural pack
built from the documented schema has it nested under `time_summary` and nowhere else.
The workbook then renders it and the deck does not.

**Why no harness caught it:** check_pack.py:148 synthesizes its pack.json with
`scoring_model_version` at the top level — a shape the SKILL never instructs anyone to
produce. So 427 assertions a seed pass against a fixture whose shape the documented
process does not generate. That is the same class of gap as step 9's SigV4 finding:
the harness agreed with itself.

**What did work:** house-format/assets/self-check.md caught it before publishing, which
is exactly what it is for. The run fixed it and shipped a correct deck — both decks,
step 9's and step 10's, read "Scoring model v1.0" on slide 1. The defect costs a rebuild
cycle, not a wrong artifact, and only because the self-check is in the Skill.

Fix is one line twice: give build_deck.py the fallback build_workbook.py already has,
and add the nested-only shape to check_format.py. Not done here — step 10 changed no
Skill, and keeping that true is worth more than folding an unrelated fix into it.
